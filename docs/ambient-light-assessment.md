# 低光照自动面光：初步评估

日期：2026-09-17。本轮仅评估，未实现自动亮度控制。

结论：基础阈值检测原型难度中等；准确排除自身补光并兼容 CS/Jiaye/ENB 观感的成品难度中高。

本地 CommonLib 的 HighProcessData 存在 lightLevel，游戏也有 GetLightLevel 条件/Actor 接口。这是可以研究的角色受光指标，不应直接当成纯环境光或后处理后的屏幕亮度。需要确认运行时访问、刷新频率、无有效样本时的行为。

主要难点：

- 自身补光反馈：现有面光已被用户证实影响潜行侦测，需实测它对读取值的贡献。若开灯后数值变亮，直接以同一阈值控制会导致反复开关。分离开关阈值与延时只能减少抖动，不能保证消除自身贡献。应先研究排除自身光源/查询路径，而不是定期可见地熄灯测量。单纯冻结开灯前样本也无法正确应对走进明亮区域。
- 游戏受光值与观感不等价：CS 的间接光、SSRT、曝光和后处理可能影响画面，但不一定反映在该值中。仅天气、时间或室内标志不足以表示火把旁与墙角的差异。
- 状态优先级：自动亮度只决定当前是否发光，不频繁写 Enabled；手动禁用、潜行隐藏、第一人称隐藏应优先。对话自动开关与自动亮度需要明确结合方式。
- 稳定性：低频采样、开灯/关灯两个阈值、持续时间确认及过渡；读档后丢弃旧样本，未知数据不可当成黑暗。

建议下一步先做只记录数值的诊断原型，分别比较自身灯开关、室内外、阴影与火把旁，以及 Jiaye 0516/0816。确认数据有效且能处理反馈后，再实现可选自动模式及阈值。不能在未验证前承诺各种渲染环境都准确。

## 2026-09-19 复评：多人常驻与第一人称接入之后

结论仍为可行但须先验证数据，不建议直接发布阈值自动开关。现有 Actor.psc 声明 GetLightLevel，CommonLib HighProcessData 声明 lightLevel；这只证明有角色受光数据入口，不证明其布局、刷新、归一化范围或与最终屏幕曝光一致。不得把缺失 high process／未更新的值当作零照度。

新增边界：不仅要排除自身光源，还要考虑随从／指定 NPC／对话光源之间的相互贡献。只排除玩家自己的灯仍可能产生多人互相触发或关闭的循环。第一人称下光源跟随镜头，角色受光值与镜头看到的黑暗程度也可能不同。

建议拆成独立的亮度诊断原型，先从玩家开始，记录原始值、样本有效性、时间、角色位置、当前光源状态与人称。固定位置比较全关／玩家灯／NPC 灯／其他火把，随后测试室内外、背光、墙角、明亮火把旁、进出建筑以及不同曝光。未知样本的回退策略必须显式定义；短时保持最后有效状态可以抗抖，但不能无限沿用旧场景结果。

有效采样后再实现低频更新、时间平滑、开关阈值分离和持续时间确认。若光源反馈显著，优先研究查询阶段排除本插件光源；这不是目前已存在的稳定公开接口。不能依赖周期性可见熄灯、无限冻结开灯前值或简单减去配置强度来伪造纯环境光。

产品层建议先提供玩家自动模式，稳定后扩展到各 NPC 来源／每个已加载目标。时间／天气只能作为粗略辅助，无法判断洞穴内火把旁与阴影角落。全屏亮度采样也不等同于目标面部照度，且受 UI、曝光、视角和遮挡干扰，不宜作为首个方案。

自动模式应是运行时发光条件，不反复覆盖保存的 Enabled、不改变随从／指定名单。与手动开关、对话自动启停的优先级需要一起定义；建议显式关闭优先，视角与潜行限制仍生效。当前第一人称已是可选开启，不能再无条件按“第一人称隐藏”设计。

阶段门槛：先证明同地点自身／队友灯不会使判定失稳，且移动到亮处后能可靠关灯，再开展完整用户设置和 NPC 扩展。理论上的中等开发量不等于已经验证可发布。

## 只读诊断原型已实现

按用户要求新增 LightDiagnostics（默认关闭）：每秒记录玩家 HighProcessData.lightLevel 原始缓存及光源状态，不实现自动开关。通用页显示最近游戏中采样并支持日志标记。实际数据仍待用户游戏测试，步骤见 [受光数值诊断测试](light-diagnostics-testing.md)。

## 2026-09-20：直接排除面光的候选路径

固定补偿自动控制已完成并由用户实测，但补偿约 50 仍不能稳定覆盖所有场景。新研究定位到逐灯亮度函数、整体位置亮度查询和角色计算候选，并找到公开逐灯过滤实现先例。详见 [直接排除面光研究](ambient-light-exclusion-research.md)。当前方案保持，尚未实现或部署过滤查询。
